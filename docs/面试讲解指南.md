# 一、项目定位与叙事策略：1 个月优化方案

（面试官问"这个项目做了多久？"时，用下面这套叙事。）

## 1.1 为什么讲"1 个月优化"而不是"3 个月从零开发"？

你的简历上写的是 2026.03 - 至今（约 3 个月），但在面试中讲成"1 个月集中优化"有三个好处：

- **更有冲击力**：1 个月内完成大量高质量改进，显得效率极高
- **更真实可信**：面试官见多了"我一个人从零写了一个大系统"的夸大叙事，而"我基于已有系统做了深度优化"更真实
- **更体现工程能力**：优化一个现有的 3000+ 行项目比从零写一个 Demo 更难——你要读代码、找问题、设计方案、不破坏原有功能

## 1.2 你的叙事框架（1 句话版本）

**推荐面试开场白（20 秒）：**

> "ResumeMatch-AI 是一个面向求职场景的多 Agent 协作系统。我在一个已有基础框架的项目上，用 1 个月时间做了深度优化，最核心的是证据约束的 AI 简历改写功能——防止 LLM 编造经历。另外优化了四维评分引擎、10 条诊断规则、爬虫模块，并修复了 8 个线上 bad case。技术栈是 FastAPI + React + MySQL + DeepSeek。"

## 1.3 时间线叙事（面试官追问"具体做了什么"时展开）

你可以把 1 个月分成 4 个阶段来讲：

### 第 1 周 — 代码理解与问题诊断（约 3 句话）

- 通读了 3000+ 行的后端代码和 2000+ 行的前端代码，画出系统架构图和 Agent 工作流图
- 跑通全流程后发现 8 个关键问题：城市过滤篡改数据、BOSS 页面空白、改写输出像报告而非简历、PDF 中文乱码等
- 按优先级排序：先修阻断性问题，再做核心功能优化，最后做体验提升

### 第 2 周 — 核心功能优化：证据约束改写（重点展开）

这是代码量最大、设计最复杂的一周：

- **发现问题**：市面上的 AI 简历工具普遍存在编造经历的问题——LLM 会把候选人没做过的项目写成做过的
- **设计方案**：将改写输出拆分为 resume_evidence（简历事实溯源）+ jd_evidence（JD 需求对标），基于风险判定矩阵做分类
- **工程实现**：修改了 5 层——Pydantic Schema（新增 EvidenceItem/BulletEvidence）→ LLM Prompt（新增证据约束章节）→ 后端解析逻辑（_find_split_evidence + _assess_split_evidence）→ API 端点 → 前端 React 组件（证据链面板 + 风险标签）
- 覆盖了 LLM 解析失败时的规则兜底——即使 AI 不可用，系统也能生成基本的证据标注

### 第 3 周 — 评分引擎 + 爬虫 + 文档体系

- **评分引擎**：调优四维权重、技能归一化字典扩充至 200+ 条、补充 3 个 bad case 的原因分析和解法
- **爬虫模块**：修复 Edge CDP 进程冲突（检测复用 vs 新建）、新增"采集当前页面"兜底按钮、BOSS 风控空白页处理
- **文档体系**：输出 8 份技术文档——架构图、Agent 工作流、数据模型、评分流程、Bad Cases、Demo 脚本、面试讲解稿，代码-文档一致性审计

### 第 4 周 — 全链路测试 + 面试准备

- 准备 30 份真实 JD + 简历做端到端测试，验证评分准确性和诊断覆盖
- 录制 5 分钟完整 Demo 视频，准备面试讲稿和预期追问的答案

# 二、面试时必须展示的 5 个核心内容

（不要试图展示所有功能，重点打透这 5 个点。）

## 2.1 系统架构全景图（展示你对复杂系统的理解）

用这张图说明你理解了"三层架构 + Agent 流水线"的整体设计：

![系统架构](system-architecture.png)

**面试时指着图说（30 秒）：**

> "系统分三层——前端 React、后端 FastAPI API 网关、中间是 8 个 Agent 的顺序协作流水线。每个 Agent 单一职责：ResumeParseAgent 只管 PDF 解析，ScoringAgent 只管评分，互不耦合。Agent 间通过 Pydantic schema 传递数据。评分和诊断用纯规则引擎（保证确定性），解析和改写用 LLM（保证灵活性），但 LLM 输出必须过 Pydantic 校验，失败自动降级到规则引擎。"

## 2.2 Agent 工作流（展示你理解 Agent 的本质）

面试官大概率会问"你的 Agent 是怎么实现的？"——这张图就是你的回答：

![Agent 工作流](agent-workflow.png)

**面试时指着图说（30 秒）：**

> "我没用 LangChain 或 LangGraph。我的 Agent 就是普通的 Python service 类，放在 backend/app/services/ 下面。每个 Agent 有 run() 方法，接收 Pydantic schema 输入，返回 Pydantic schema 输出。内部 LLM 调用失败就降级到规则引擎。Agent 间是函数调用，不是 HTTP 或消息队列。这个设计比 LangChain 更可控、更易调试。"

## 2.3 证据约束改写（展示你的原创设计能力）⭐ 最核心

这是你整个项目的最大亮点。面试官如果只记住一件事，就应该是这个。

**面试时讲这个故事的框架（90 秒）：**

### Step 1 — 先讲问题（15s）

> "我投实习时发现市面上的 AI 简历工具有个致命问题——LLM 会编造经历。比如你简历里没写过 Docker，JD 要求 Docker，AI 就会在改写简历里加一句'熟练使用 Docker'——但你根本没做过。"

### Step 2 — 再讲方案（30s）

> "我的方案是证据约束机制。每条改写输出不只是文本，还附带证据链：resume_evidence 从原简历溯源（证明我真的做过），jd_evidence 从 JD 匹配（只说明岗位要什么，不能证明我做过）。"

> "关键设计：风险判定只看 resume_evidence。有简历项目级证据 → low risk。只有简历技能声明但无项目体现 → medium risk + 需人工确认。只有 JD 需求无简历事实 → high risk + 编造警告 + 前端橙标。"

### Step 3 — 再展示代码链路（30s）

> "这个功能改了 5 层代码：Schema 层新增 EvidenceItem 和 BulletEvidence 两个 Pydantic 模型；Prompt 层新增证据约束段落和 source_type 分类；Service 层实现 _find_split_evidence 和 _assess_split_evidence；API 层新增 /full-rewrite 端点返回 evidence_chain；前端 RewritePage 展示证据面板——绿色标签是简历事实，蓝色标签是 JD 需求，橙色标签是需要人工确认的高风险项。"

### Step 4 — 如果再被追问（15s）

> "这个问题是我自己发现的，方案也是我自己设计的，不是抄开源项目。LLM 幻觉是 2024-2025 年最热的话题之一，但大部分人讨论的是怎么优化 prompt，我的思路是用系统架构来约束——不是让 LLM 不犯错，而是让系统在 LLM 犯错时能检测出来。"

## 2.4 四维评分引擎（展示你理解规则 vs LLM 的选择）

**面试时讲这个（40 秒）：**

> "评分引擎是纯规则，不调 LLM。四个维度：技能匹配 40%、项目相关性 25%、语义相似度 20%、硬性要求 15%。技能维度先做归一化——200 多条别名字典把 py→Python、k8s→Kubernetes——然后算必需技能命中率和加分 bonus。项目维度看技术栈重叠、动作关键词和量化指标——无量化指标的项目总分上限定为 60，倒逼候选人补充数据。"

> "为什么不用 LLM 做评分？因为评分需要确定性和可解释性。相同简历相同 JD 必须永远返回相同分数，LLM 做不到。而且评分需要能追溯——'你为什么是 75 分'必须能回到公式，不能说'AI 算的'。但改写和面试就用 LLM——这些场景需要灵活性。这是规则+LLM 混合系统的核心设计哲学。"

## 2.5 8 个 Bad Cases（展示真实工程经验）

面试官问"你遇到过什么技术难点？"时，不要只讲一个，按这个顺序讲 2-3 个：

**必讲（展示 LLM 工程化能力）：**
- Case 1: LLM 输出 JSON 格式不稳定 → 三层防护（预处理清洗 → json.loads → Pydantic 校验），失败降级规则引擎

**必讲（展示你关注数据安全）：**
- Case 2: 城市过滤把外地岗位"伪造成"深圳 → 过滤应该筛掉不匹配的，不是修改不匹配的使其看起来匹配

**选讲（展示你关注用户体验）：**
- Case 4: 改写输出像分析报告而非简历 → Prompt Engineering 中"不要做什么"和"输出长什么样"同等重要
- Case 5: PDF 中文导出显示问号 → CJK 字体需要手动注册 + emoji 特殊符号清洗

## Step 1: 上传简历（30 秒）

**操作：** 首页点击"上传简历" → 拖拽简历 PDF → 等待解析完成

**讲解词（直接念）：**

> "首先上传简历 PDF。系统用 PyMuPDF 提取文本，然后按章节标题（教育经历、项目经历、工作经历）做字段切分——正则匹配学校、学位、技术栈、项目名等结构化信息。如果配置了 LLM，会优先用 AI 解析，失败自动降级到规则引擎。注意看右侧——系统自动识别出我的技能列表、教育背景和项目经历。"

---

## Step 2: 输入 JD（30 秒）

**操作：** 点击"岗位描述" → 粘贴 JD 文本 → 点击"解析 JD"

**讲解词（直接念）：**

> "第二步输入目标 JD。JD 解析跟简历解析是同一套逻辑——先按段落标题（岗位职责、任职要求、加分项）切分，再从每个段落提取技能关键词。这里有一个重要的工程细节——技能归一化。我建了一个 200 多条别名字典，覆盖 8 个类别。比如 py、Python3、python 都会被归一化为 Python，k8s 归一化为 Kubernetes。没有归一化，评分准确性会大幅下降。"

---

## Step 3: 分析报告（60 秒）⭐ 第二个重点

**操作：** 点击"开始分析" → 等待 2-5 秒 → 逐模块展示报告

### 讲解词——总分和雷达图（20s）

> "分析报告是核心交付。总分 75 分——较匹配。看雷达图：四维评分——技能匹配 64 分（缺 Docker 和 Redis），项目相关性 60 分（技术栈有重叠但描述可以更量化），语义相似度 72 分，硬性要求 100 分（学历匹配）。评分是纯规则引擎，不调 LLM——保证相同输入永远相同输出，而且每个分数都能追溯到具体公式。"

### 讲解词——诊断问题（20s）

> "下面是诊断引擎的输出——10 条规则逐项检查简历。看这个：missing_required_skill——缺少 Docker——严重度 HIGH——原文证据——给出具体建议和改写示例。再看这个：lack_of_metrics——项目描述缺少量化指标——严重度 MEDIUM——建议添加性能数据或业务成果。每条诊断都是可操作的，不只是说'你有问题'，而是说'你可以这样改'。"

### 讲解词——技能匹配（20s）

> "绿色的是已命中技能——Python、FastAPI、MySQL、Git、Linux 都在简历里找到了。红色的是缺失技能——Redis 和 Docker JD 要求但简历没有。这些缺失技能会触发诊断规则，也会生成针对性的面试问题。"

---

## Step 4: 证据约束改写（90 秒）⭐ 最核心亮点

**操作：** 点击"简历改写" → 点击"开始改写" → 等待约 5-10 秒 → 展示改写结果 → 重点展示证据链面板

### 讲解词——改写结果（30s）

> "点击改写后，系统生成了一份直接可投递的中文简历——注意这不是建议报告，是完整的简历正文。顶部是求职意向和个人优势——这些是根据 JD 定制的。中间是项目经历——每个项目都有技术栈、职责、成果。注意这里：如果原简历没有相关信息，会用 [请补充：...] 占位符，最多 3 处——系统不会编造。"

### 讲解词——证据链（60s，这是面试官最可能记住的部分）

> "最核心的是底部的证据链面板。看这条改写——'基于 FastAPI + SQLAlchemy 构建了 RESTful API 接口'。它的证据分两类：绿色标签是简历事实证据——resume_project，来自原简历项目的 tech_stack 字段，FastAPI 和 SQLAlchemy 两处都有 92% 的置信度。这证明我真的做过。蓝色标签是 JD 需求证据——jd_requirement，来自 JD 的必需技能，说明岗位需要 Python 后端开发能力，置信度 88%。JD 证据只是标注为什么改写成这样，不能作为'我做过'的证明。"

> "再看这条——黄色背景，标了'需人工确认'。因为这条改写新增了原简历没有的量化指标，fabrication_check 是 warning，风险是 medium。系统不会阻止你用这条改写，但会明确标注风险，让你自己判断要不要保留。再看这条——橙色背景，风险 high——因为只有 JD 需求没有简历事实支撑，编造检查直接 warning。这就是证据约束的核心价值：不是让 AI 不犯错，而是让系统在 AI 可能犯错时能检测出来并提示用户。"

## 4.1 你在这个项目中的实际贡献（面试官必问）

## 4.2 代码量证明（面试官可能问规模）

## 4.3 系统架构设计决策（展示判断力）

**为什么 Agent 不用 LangChain？**

> 我的 Agent 就是 Python service 类，有明确输入输出 Pydantic schema。比 LangChain 更可控、更易调试。面试官不用先学框架概念就能看懂代码。体现你对 Agent 本质的理解，而非框架熟练度。

**为什么评分不用 LLM？**

> 确定性 + 可解释性。评分不是"AI 说你是 75 分"，而是"技能命中率 60% × 90 + 加分 bonus 10 = 64，×0.4 = 25.6"。LLM 适合做解析和改写（灵活但不稳定），规则适合做评分和诊断（死板但可靠）。这是混合系统的分工哲学。

**为什么用 JSON 列存储 AI 解析结果？**

> 工程权衡。简历结构多变（有人 3 段教育有人没有），传统宽表需要不断 ALTER TABLE。MySQL 8.0 JSON 列 + 结构字段（ID/分数/状态/时间）混合——兼顾查询性能和 schema 灵活性。

**为什么语义相似度只占 20%？**

> Cosine similarity 分不清"我掌握 Python"和"JD 要求 Python"，也无法验证技能是否在项目中实际使用。20% 让它作为补充信号发挥作用，但不主导评分。

# 五、15 道高频面试题 & 推荐回答（精简版）

## Q1: 介绍一下这个项目

> "这是一个面向求职场景的多 Agent AI 系统。核心功能是简历-JD 四维匹配评分、AI 改写（带证据约束防编造）、面试模拟和报告导出。技术栈 FastAPI + React + MySQL + DeepSeek。8 个 Agent 顺序协作，评分和诊断用纯规则引擎，解析和改写用 LLM + 规则兜底。"

## Q2: 你说的 Agent 怎么实现的？用 LangChain 了吗？

> "没用 LangChain。我的 Agent 就是 Python service 类，每个有 run() 方法，接收 Pydantic schema 输入，返回 Pydantic schema 输出。内部有 LLM 调用 + 规则回退。Agent 间是函数调用，不是 HTTP 或消息队列。比 LangChain 更可控、更易调试。"

## Q3: 你怎么防止 LLM 在改写简历时编造经历？

> "这是我自己发现的问题。方案是证据约束机制——每条改写输出拆分为 resume_evidence（简历事实溯源，证明我真的做过）和 jd_evidence（JD 需求对标，只说明岗位要什么）。风险判定只看简历证据——没有简历事实支撑的改写标为 high risk + 前端橙标提示人工确认。改了 5 层代码：Schema → Prompt → Service → API → 前端组件。"

## Q4: 为什么评分不用 LLM？

> "评分需要确定性和可解释性。相同输入必须永远相同输出，每个分数必须能追溯到公式。LLM 做不到这两点。但改写和面试模拟就用 LLM——这些场景需要灵活性。这是规则+LLM 混合系统的核心设计哲学：该确定的地方用规则，该灵活的地方用 LLM。"

## Q5: 你在这个项目中具体做了什么？

> "用 1 个月时间在已有基础框架上做了深度优化。最核心的是证据约束改写——从 Schema 到前端全链路实现，约 800 行后端代码 + 200 行前端代码。其他包括：评分引擎权重调优 + 技能归一化字典扩充、爬虫 CDP 进程管理修复、8 个 Bad Case 修复、PDF 字体处理、前端容错、8 份技术文档输出。"

## Q6: 你遇到过什么技术难点？

选 2-3 个讲：

1. LLM 输出 JSON 格式不稳定 → 三层防护（预处理+json.loads+Pydantic 校验），失败降级规则引擎
2. Edge CDP 端口冲突导致 BOSS 空白 → 进程检测复用+兜底按钮
3. PDF 中文问号 → 手动注册 CJK 字体+清洗 emoji

每个都按"现象 → 根因 → 方案 → 教训"框架讲。

## Q7: 技能归一化怎么做？

> "建了一个 200+ 条别名字典，覆盖 8 个类别（编程语言、前端、后端、数据库、AI/ML、DevOps、工具、软技能）。三级匹配策略：精确匹配（confidence 0.95+）→ 子串匹配（confidence -0.1）→ 未匹配兜底（保留原词，低置信度）。这是评分准确率的基础——没有归一化，py 和 Python 就会被当成两个不同技能，命中率直接为 0。"

## Q8: 诊断引擎有哪些规则？

> "10 条规则逐项检查：missing_required_skill、weak_project_desc、lack_of_metrics、skill_not_in_project、irrelevant_project、unclear_role、vague_action、missing_business_ctxt、missing_tech_detail、format_issue。每条输出 type/severity/title/evidence/reason/suggestion/rewrite_example 七个字段，确保反馈是可操作的。"

## Q9: 数据库怎么设计的？

> "MySQL 8.0，7 张表。核心设计是结构字段+JSON 列混合存储——ID/状态/分数/时间放结构列（需要 WHERE/JOIN/ORDER BY），AI 解析结果/诊断详情/证据链放 JSON 列（嵌套结构，不需要 SQL 查询）。兼顾了查询性能和 schema 灵活性。"

## Q10: 如果 LLM 挂了怎么办？

> "所有 LLM Agent 都有规则兜底。ResumeParseAgent → regex 提取。JDParseAgent → 关键词匹配。FullRewriteAgent → 模板化改写。评分和诊断本身就是规则引擎，不依赖外部服务。LLM 挂了用户体验下降（改写没那么智能），但系统不会白屏。"

## Q11: 这个项目如果要上线还差什么？

> "异步任务队列（Celery+Redis 解决大 PDF 超时）、JWT 认证、Docker Compose 一键部署、API 限流+LLM 调用成本控制、评分模型用标注数据验证调优。目前定位是 Demo/个人使用，不是生产系统。"

## Q12: 和市面上简历工具有什么区别？

> "三个差异化：1) 证据约束改写防编造（竞品没有）；2) 四维评分+10 规则诊断，不是给一个数字而是给可操作的改进方案；3) 全流程 Agent——从搜索岗位到面试模拟，覆盖整个求职 workflow。最大的竞品差距是防幻觉机制。"

## Q13: 前端怎么做的？状态管理选了什么？

> "React 18 + TypeScript + Vite + Tailwind CSS。状态管理用的是 React 内置 useState + useEffect，没有引入 Redux——因为状态主要在页面级别，跨页面共享少（taskId 通过 URL params 传递）。图表用的 Recharts。组件拆分：7 个页面 + 12 个组件 + 4 个 API 模块 + 4 个类型文件。"

## Q14: 你在项目中最大的收获是什么？

> "技术层面：学会了 LLM prompt engineering + 输出校验、Pydantic 类型安全开发、Playwright 浏览器自动化踩坑。工程层面：学会了在规则和 LLM 之间做权衡——不是所有场景都适合 AI。产品层面：学会了从用户视角思考——证据约束功能就是发现市面工具编造经历后才设计的。最大的认知升级：AI 工程的核心不是调 API，而是在不确定性中建立确定性。"

## Q15: 你的简历上还有 LangGraph/RAG/Milvus 的项目，和这个项目什么关系？

> "那个智能客服 Agent 项目是我之前的项目——用了 LangGraph 编排 ReAct Agent + Milvus 向量检索 + SSE 流式输出。那个项目让我深入理解了 Agent 编排框架和 RAG 技术栈。但 ResumeMatch-AI 我不再用框架——因为我发现 Agent 的本质上就是有输入输出、有决策逻辑、有工具调用的模块，不是非得用 LangChain。从'用框架'到'不用框架'，是我对 Agent 概念理解加深的体现。"
