# 第二阶段：问题诊断（第 3-4 天）

## 2.1 你发现了什么问题？

跑通全流程后，你按严重程度整理出 **8 个关键问题**：

| # | 问题 | 现象 | 严重度 | 影响范围 |
|---|------|------|--------|---------|
| 1 | LLM 输出 JSON 不稳定 | 同一份简历问两次，第一次返回合法 JSON，第二次多了 trailing comma 导致解析失败，页面 500 | 🔴 阻断 | 所有 LLM 功能 |
| 2 | 简历改写像"建议报告"而非"简历" | 改写输出大段分析性文字，"建议你补充..."这类表述，用户要的是直接能投的简历正文 | 🔴 阻断 | 改写功能 |
| 3 | 城市过滤篡改数据 | 智联搜索结果中成都、苏州的岗位，被系统把城市字段改成深圳，显示为"深圳"岗位 | 🟡 严重 | 爬虫搜索 |
| 4 | BOSS 页面空白 | Edge CDP 端口冲突，两个进程抢同一个用户目录，浏览器打开但页面空白 | 🟡 严重 | BOSS 搜索 |
| 5 | PDF 导出中文显示问号 | ReportLab 默认字体不支持 CJK，中文全部显示为 "?" | 🟡 严重 | 报告导出 |
| 6 | 前端字段为空导致白屏 | 后端某些字段返回 null，前端直接访问报错，整页崩溃 | 🟡 严重 | 报告页面 |
| 7 | 改写缺少证据溯源 | 改写输出只有结果没有依据——你不知道 LLM 是优化了措辞还是编造了经历 | 🟢 重要 | 改写可信度 |
| 8 | 无架构文档 | 代码能跑但没人能讲清楚系统怎么设计的，面试时只能"这个页面有这个功能" | 🟢 重要 | 面试展示 |

## 2.2 你怎么排优先级？

你把问题分了三个梯队：

- **第一梯队（阻断性）**：LLM JSON 解析失败 → 系统不可用，必须最先修
- **第二梯队（体验性）**：改写输出格式、城市过滤、BOSS 空白、PDF 问号、前端白屏 → 功能可用但体验差
- **第三梯队（增强性）**：证据溯源、架构文档 → 加分项，决定面试竞争力

# 第三阶段：方案设计（第 5-7 天）

## 3.1 你是先设计再写代码，不是边写边想

针对每个问题，你都是先出方案、再写代码：

### 问题 1：LLM 输出 JSON 不稳定

**你设计的方案**：三层防护体系

```
LLM 原始输出
  → 第一层：文本预处理（提取 ```json 代码块、移除 trailing comma）
  → 第二层：json.loads() 解析
  → 第三层：Pydantic 严格校验
  → 任何一层失败 → 降级到规则引擎
```

**为什么不是"优化 prompt"？** 因为 prompt 优化只能降低概率，不能根治。LLM 本质是非确定性的，必须用工程手段兜底。

![Agent 工作流](agent-workflow.png)

### 问题 2：改写像报告而非简历

**你设计的方案**：在 Prompt 中增加硬性输出约束

你修改了 `full_resume_rewrite.md`，新增了关键约束语句：
- "你要输出一份'可以直接投递'的中文简历，不是建议列表，不是分析报告"
- "[请补充：...] 占位符只在原简历完全没有相关信息时才使用，且最多 3 处"
- "不要输出'原简历未提供'这类描述——直接利用已有信息写出最好的版本"

**设计思路**：LLM 默认倾向分析性回复。Prompt engineering 的关键不（仅）是告诉它"做什么"，更重要的是告诉它"不要做什么"+"输出长什么样"。

### 问题 7：改写缺少证据溯源（最核心的设计）

**你发现这个问题的过程**：你在用市面上的 AI 简历工具时发现——它们会把你没做过的项目写成你做过。JD 要求 Docker，你简历里没有 Docker，AI 就在改写简历里加一句"熟练使用 Docker"。这对求职者是致命的。

**你设计的方案：证据约束机制**

核心思路：把每条改写输出拆分为两类证据，不可混淆。

```
resume_evidence（简历事实证据）——证明"我真的做过"
  - source_type = "resume_project"：原简历项目中的技术栈/描述/成果
  - source_type = "resume_skill"：原简历中的技能声明
  - source_type = "resume_work_experience"：原简历中的工作/实习经历
  - source_type = "resume_education"：原简历中的教育背景

jd_evidence（JD 需求证据）——只说明"岗位需要什么"，不能证明我做过
  - source_type = "jd_requirement"：JD 必需技能/职责
  - source_type = "jd_preferred"：JD 加分项
```

**风险判定矩阵（驱动于 resume_evidence）：**

| 情况 | risk | fabrication_check | need_manual_confirm |
|------|------|-------------------|---------------------|
| 有简历项目级证据 + JD 需求对应 | low | passed | false |
| 简历技能区有证据，项目证据弱 | medium | passed | true |
| 只有 JD 需求，无简历事实证据 | **high** | **warning** | **true** |
| 新增了原简历没有的量化指标 | **high** | **warning** | **true** |
| "参与"→"主导"但原文无依据 | **high** | **warning** | **true** |
| 改写仅优化表达、未新增事实 | low | passed | false |

**关键设计原则**：JD 写了"要求 Kubernetes"但你原简历没有 K8s 相关项目——改写结果里就算出现了 Kubernetes，也必须有 resume_evidence 支撑，否则就是编造。

![评分与诊断流程](scoring-flow.png)

**全链路实现（5 层修改）**：

| 层 | 文件 | 改动 |
|----|------|------|
| Schema 层 | `schemas/rewrite_resume.py` | 新增 EvidenceItem + BulletEvidence 两个 Pydantic 模型 |
| Prompt 层 | `prompts/full_resume_rewrite.md` | 新增证据约束章节，明确 source_type 分类和风险判定标准 |
| Service 层 | `services/resume_rewrite_service.py` | 实现 _find_split_evidence() 和 _assess_split_evidence() |
| API 层 | `api/v1/endpoints/analysis.py` | /full-rewrite 端点返回 evidence_chain |
| 前端层 | `pages/RewritePage.tsx` + `api/analysisApi.ts` | 证据链面板：绿色=简历事实，蓝色=JD需求，橙色=需确认 |

# 第四阶段：开发实施（第 8-21 天，约 2 周）

## 4.1 你实际做了什么

按优先级逐项落地：

### 第 2 周（第 8-14 天）：核心功能 + 阻断性问题

**前半周 — 证据约束改写（最大工作量）**
- 修改 Pydantic Schema：新增 EvidenceItem（7 种 source_type）、BulletEvidence（resume_evidence + jd_evidence 拆分 + risk + fabrication_check + need_manual_confirm）
- 修改 LLM Prompt：新增证据约束章节，明确"JD 证据不能证明你做过"的规则
- 重写 Service 证据逻辑：_parse_evidence_list() 解析 LLM 返回的证据字典 → _find_split_evidence() 分别查找简历侧和 JD 侧的支撑 → _assess_split_evidence() 基于简历证据做风险判定
- 保证 LLM 失败时的规则兜底：规则模式也生成 evidence_chain，只是置信度较低
- 前端 RewritePage 重写证据链面板：绿色标签（简历事实），蓝色标签（JD 需求），橙色标签（需人工确认），风险/编造检查 badge

**后半周 — LLM 稳定性 + 改写格式**
- 实现三层 JSON 解析防护
- 重写改写 Prompt：从"分析建议"模式改为"直接投递简历"模式

### 第 3 周（第 15-21 天）：修复 + 增强

- **评分引擎优化**：调优四维权重配比，技能归一化字典扩充至 200+ 条覆盖 8 个类别，新增三级匹配策略（精确→子串→兜底）
- **爬虫模块修复**：Edge CDP 进程复用检测（已运行→复用，未运行→新启动），新增"采集当前页面"兜底按钮，BOSS 风控空白页处理
- **城市过滤修复**：从"修改不匹配的数据使其看起来匹配"改为"硬过滤：只保留 city == target_city 的岗位"
- **PDF 导出修复**：ReportLab CJK 字体注册（TTFont），emoji/箭头/特殊符号清洗，Word 字体同步设置 eastAsia
- **前端容错**：ReportPage 全字段可选链 + 空值默认值，InterviewPage 状态兼容
- **评分诊断增强**：明确 10 条诊断规则，每条输出 type/severity/title/evidence/reason/suggestion/rewrite_example 七个字段

# 第五阶段：验证测试（第 22-25 天）

## 5.1 你怎么验证改对了？

- **端到端测试**：准备 30 份真实 JD + 简历，跑完整流程（上传→解析→评分→诊断→改写→导出），验证每步输出正确
- **Bad Case 回归**：把之前发现的 8 个问题逐一复现，确认全部修复
- **LLM vs 规则对比**：同一份简历分别用 LLM 模式和 Mock 模式运行，确保两者输出结构一致
- **前端编译检查**：`npm run build` + TypeScript 类型检查，确保无编译错误
- **Python 编译检查**：`python -m compileall backend/app`，确保无语法错误

## 5.2 你整理了 8 个 Bad Cases

每个 bad case 都按"现象→根因→方案→教训"的框架整理，用于面试展示：

| Case | 现象 | 根因 | 教训 |
|------|------|------|------|
| 1. LLM JSON 不稳定 | 两次调用返回不同格式 | LLM 非确定性 | 三层防护，不信任单一解析 |
| 2. 城市过滤篡改数据 | 外地岗位显示为深圳 | 过滤=修改而非排除 | 数据完整性优先于展示便利 |
| 3. BOSS 页面空白 | CDP 端口冲突 | 多进程争用用户目录 | 进程管理比 DOM 选择器更难 |
| 4. 改写像报告 | 输出大段分析文字 | Prompt 缺少输出格式约束 | "不要做什么"和"输出什么样"同等重要 |
| 5. PDF 中文问号 | 中文显示为 ? | 默认字体不支持 CJK | 英文工具链做中文需要额外处理 |
| 6. 前端白屏 | 字段为空时崩溃 | 未做空值防御 | AI 输出不可靠，前端必须容错 |
| 7. 薪资解析失败 | "15k"未被识别 | 正则大小写敏感 | 正则覆盖面决定数据完整率 |
| 8. 项目切分错误 | 一个项目切成多个 | 空行是弱切分信号 | 标题关键词是更强的切分信号 |
