1. 系统总览架构

三层架构 + Agent 流水线

系统遵循经典三层架构，在业务逻辑层引入 8 个 Agent 的顺序协作流水线。

层技术选型职责
前端React 18 + TypeScript + Vite + Tailwind7 个页面覆盖完整求职工作流，12 个组件
API 网关FastAPI + Pydantic v24 个路由模块，自动生成 OpenAPI 文档
Agent 流水线Python Service 类（非 LangChain）8 个 Agent 顺序协作，LLM 优先 + 规则兜底
数据层MySQL 8.0 + 文件存储7 张表，结构字段 + JSON 列混合存储

8 个 Agent 一览

#Agent职责LLM?
①ResumeParseAgentPDF → 结构化简历可选
②JDParseAgentJD 文本 → 结构化需求可选
③ScoringAgent4 维评分 (0-100)纯规则
④DiagnosisAgent10 条诊断规则纯规则
⑤FullRewriteAgent证据约束简历改写LLM
⑥InterviewAgent15 题 + AI 模拟面试LLM
⑦ReportAgent生成 Word/PDF 报告纯规则
⑧CrawlerAgentBOSS/51job/智联/猎聘抓取Playwright

面试讲解要点

"系统分三层——前端 React、后端 FastAPI API 网关、中间是 8 个 Agent 的顺序协作流水线。每个 Agent 单一职责，通过 Pydantic schema 传递数据。评分和诊断用纯规则引擎保证确定性，解析和改写用 LLM 保证灵活性，但 LLM 输出必须过 Pydantic 校验，失败自动降级到规则引擎。"

2. Agent 工作流

完整的顺序协作流水线

从 PDF 到面试的完整链路：

上传 PDF → ① ResumeParseAgent（LLM extract → regex fallback）→ ParsedResume
粘贴 JD → ② JDParseAgent（LLM extract → regex fallback）→ ParsedJD
点击分析 → ③ ScoringAgent（4-dim score, no LLM）+ ④ DiagnosisAgent（10-rule check, no LLM）→ MatchReport
→ ⑤ FullRewriteAgent（LLM + 证据链）→ Rewritten Resume
→ ⑥ InterviewAgent（LLM + 模板）→ 15 Questions
→ ⑦ ReportAgent（no LLM）→ Word/PDF 导出

为什么拆成多个 Agent？

  • 单一职责 — 每个 Agent 只做一件事，可独立测试、独立改进
  • 类型安全 — Agent 间通过 Pydantic schema 传递数据，不会在传递中变形
  • 回退隔离 — 某 Agent LLM 失败不影响其他 Agent，规则引擎独立可用
  • 可调试性 — 每个 Agent 的输入输出都可以打日志，评分不对看 ScoringAgent 中间结果

面试讲解要点

"我没用 LangChain 或 LangGraph。我的 Agent 就是普通的 Python service 类，放在 backend/app/services/ 下面。每个 Agent 有 run() 方法，接收 Pydantic schema 输入，返回 Pydantic schema 输出。Agent 间是函数调用，不是 HTTP 或消息队列。这个设计比 LangChain 更可控、更易调试。"

3. 数据模型与数据库设计

7 张核心表

resumes ──1:N── analysis_tasks ──1:1── match_reports

job_descriptions ──1:N── analysis_tasks

analysis_tasks ──1:0..1── rewritten_resumes，──1:N── interview_questions

cached_job_searches（独立缓存表）

核心设计：结构字段 + JSON 列混合

结构字段（需要 WHERE / JOIN / ORDER BY）：ID、外键、状态、分数、时间

JSON 列（嵌套数据，不需要 SQL 查询）：AI 解析结果、诊断详情、证据链

面试讲解要点

"MySQL 8.0，7 张表。核心设计是结构字段 + JSON 列混合存储——需要查询排序的（ID、状态、分数、时间）放结构列，AI 解析结果（嵌套的简历结构化数据、诊断详情、证据链）放 JSON 列。兼顾了 SQL 查询性能和对非结构化 AI 输出的灵活性。不是偷懒，是工程权衡。"

4. 评分与诊断流程

四维评分公式

total_score (0-100) = skill_score × 0.40 + project_score × 0.25 + semantic_score × 0.20 + requirement_score × 0.15
维度权重计算方式为什么
技能匹配40%必需技能命中率 × 90 + 加分 bonus（200+ 别名归一化）面试邀请的最强信号
项目相关性25%技术栈重叠 + 动作关键词 + 量化指标 + 描述长度技能落地的证据
语义相似度20%sentence-transformers / TF-IDF cosine similarity辅助信号（太高会被无关内容欺骗）
硬性要求15%学历层级 + 工作年限，met=100 / unknown=60 / not=30门槛检查

10 条诊断规则

#规则触发条件严重度
①missing_required_skillJD 必需技能在简历缺失HIGH
②weak_project_desc项目描述 < 50 字符MEDIUM
③lack_of_metrics全项目无数字/百分比/性能指标MEDIUM
④skill_not_in_project声明技能未在项目中体现MEDIUM
⑤irrelevant_project项目技术栈与 JD 无交集LOW
⑥unclear_role项目未明确个人角色MEDIUM
⑦vague_action"负责/参与"等模糊动词MEDIUM
⑧missing_business_ctxt缺少业务场景描述LOW
⑨missing_tech_detail未提及具体技术实现MEDIUM
⑩format_issue日期/格式不一致LOW

为什么评分和诊断都不用 LLM？

用 LLM用规则引擎
确定性❌ 相同输入可能不同输出✅ 永远相同
可解释性❌ 无法追溯"为什么"✅ 每个分数有公式可查
外部依赖❌ 依赖 API，可能超时✅ 毫秒级响应
成本❌ API 调用费用✅ 零成本

面试讲解要点

"评分引擎是纯规则，不调 LLM。四个维度：技能匹配 40%、项目相关性 25%、语义相似度 20%、硬性要求 15%。技能维度先做归一化——200 多条别名字典把 py→Python、k8s→Kubernetes。为什么不用 LLM？因为评分需要确定性和可解释性——相同简历相同 JD 必须永远返回相同分数，而且每个分数都能追溯到具体公式。LLM 做不到这两点。但改写和面试就用 LLM——这些场景需要灵活性。这是规则+LLM 混合系统的核心设计哲学。"
